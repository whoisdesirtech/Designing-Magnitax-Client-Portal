Welcome aboard · Developer Onboarding

Developing the Magnitax Secure Client Portal

This guide gets you set up and productive on the Magnitax Portal — a single-page web app for tax clients and CPA admins, built with vanilla HTML/CSS/JS on Firebase Hosting, Firestore, Storage, and Auth. You do all of your work inside Antigravity by reopening the same project folder every session — never by re-cloning it.

Repo: Designing-Magnitax-Client-Portal Live: taxagentai062026.web.app Audience: Developers Version 2.0 — Antigravity workflow

For admins: this guide pairs with the admin training that covers granting GitHub and Firebase access.

Open Admin Training →

Rule #1 — DO NOT re-clone the repository. You clone once on day one. Every time you open Antigravity after that, you reopen the existing project folder that is already on your machine. Re-cloning creates duplicates, which causes you to edit the wrong copy, lose your work, and create conflicting pull requests. If you think you need to re-clone, stop and read Section 5 first.

First-Time Setup — Clone Once

You do this one time, on day one, then never again

The repo is github.com/whoisdesirtech/Designing-Magnitax-Client-Portal. The deployable app lives in the public/ folder.

Terminal — clone ONE time
git clone https://github.com/whoisdesirtech/Designing-Magnitax-Client-Portal.git
cd Designing-Magnitax-Client-Portal

Remember the exact path of the folder you cloned into. This is your one and only working copy of the project — from now on you reopen it, you don't re-clone it.

Add the Project to Antigravity (First Time Only)

Open the Magnitax Client Portal project in Antigravity so it appears on your home screen and can be reopened with one click next session:

Open Antigravity
Choose “Add to Antigravity” (or open folder directly)
Select the folder you cloned: Designing-Magnitax-Client-Portal
Confirm it opens in Local Mode (never Agent Mode for this step)
The project now appears on your home screen — you'll reopen it there from now on

“Local Checkout” means the project is running from the files on your machine (the folder you cloned), not from the cloud. Every Antigravity project should be a local Git checkout so your edits land on real files you can commit and push.

One working copy only. You must have exactly one Magnitax project folder on your machine. Two copies = confusion, editing the wrong file, and duplicate pull requests. If you accidentally created a second copy, delete the extra one and keep the folder you've been working in.

Reopening the Project (Every Session)

The exact steps you follow every time you start working

When you open Antigravity — whether it's the first time today, or after closing it last night — do not start from scratch. You do not re-clone, you do not rebuild, you do not create a new project. You reopen the project that already exists:

Open AntigravityYour saved projects appear on the home screen
Click “Open Magnitax Client Portal Project”
Confirm you're in the same folder you cloned on day oneCheck the path
Confirm Local ModeWorking on your local checkout
Open the Terminal inside the projectAntigravity → Terminal
Sync first — Section 6 before any edits

Reopening is exactly that — reopening. All of your work, files, and history are still there. The project reopens in the state you left it. You only need to refresh it from GitHub (pull) and start the local server (Section 7).

Stop if you're about to re-clone. If you find yourself typing git clone, or creating a “new project” in Antigravity, that's the mistake this guide exists to prevent. Close that window and reopen your existing project instead.

6

Sync With GitHub Before Starting

Always start from the latest code

Before you write any code, make sure your reopened copy is up to date with the remote repository. Other developers may have merged work while you were away:

Terminal — inside the project folder
git status
# You should see: On branch main, nothing to commit, working tree clean
git pull origin main
# Pulls the latest code from GitHub into your local copy
  • If git status shows uncommitted changes you don't remember making, stop — see Section 13 (If Something Looks Different) before pulling.
  • If the pull says “already up to date”, great — you're on the latest code.
  • If the pull shows merge conflicts, don't force anything. Tell the admin — do not overwrite other people's work.

Never start work on an outdated copy. Code that changes on GitHub while you edit an old copy leads to conflicts and lost work. Sync first, every time.

Run the Portal Locally

Launch the app so you can test as you work

With the project reopened and synced, start the local server from the public/ folder. Leave this terminal running for the whole session — you'll reload it to see your changes.

Terminal — inside the project folder
cd public
npx serve .
# Portal opens at http://localhost:3000 (or similar)

Test logins: admin@magnitax.com / Password123! (CPA Admin) or jane@example.com / Password123! (Client). Any 6-digit code passes the 2FA gate in this prototype.

If the server won't start, do not create a new project or re-clone. The code is fine — check that you're in the right folder and that the terminal is inside the reopened project.

Your Daily Workflow

Branch → commit → pull request → merge

Never commit directly to main. Every change goes through a feature branch and a reviewed pull request:

Terminal — feature branch workflow
git checkout main
git pull origin main
git checkout -b feature/jf-fix-login-error
# ... edit files under public/ ...
git add .
git commit -m "feat: describe the change"
git push origin feature/jf-fix-login-error

Then open a Pull Request from your branch into main on GitHub. An admin reviews and merges it. Keep PRs small and focused, and describe what you changed and why.

Commit Message Style

  • feat: new feature or page
  • fix: bug fix
  • style: styling / theme alignment
  • chore: housekeeping (gitignore, config)
  • docs: documentation / training

Working With the Antigravity Agent

Rules for letting the built-in agent help you

Antigravity includes an AI agent you can ask to write or edit code. These rules apply to you and to the agent, so the agent never causes the same mistakes as re-cloning:

  • Work inside the reopened project. Tell the agent to work on the files in this project — the one you reopened. Never let it create a new project, a fresh folder, or a second copy.
  • Local Mode only. Keep the project in Local Mode so agent edits land on your real files. Avoid Cloud/Agent Mode for this repo unless the admin says otherwise.
  • Smallest change possible. Ask for focused edits, not rewrites. Don't let the agent rebuild working code.
  • Inspect before committing. Review the diff (git diff) after the agent edits, before you commit and push.
  • No destructive commands. The agent must never run anything that deletes, resets, or recreates the repo (git reset --hard, rm -rf, re-cloning, etc.).
  • Agent work still follows Section 10. Its edits go on a feature branch and through a pull request like yours.

One project, one folder, one truth. If the agent proposes “creating a new Magnitax project,” that is wrong. Stop it. The project already exists — we're editing the reopened copy.

Stopping Work for the Day

What to leave behind so tomorrow is painless

When you're done, leave things in a state you (or another developer) can pick up easily. Nothing here requires re-cloning or rebuilding:

  • Commit and push your branch, or leave a clear message about what's in progress. Don't leave big chunks of uncommitted work.
  • Note where you left off — in the PR description or a message to the admin — so the next session starts exactly where you stopped.
  • You can close the terminal. Closing the local server doesn't delete anything. Tomorrow you just reopen the project and run cd public; npx serve . again.
  • You can close Antigravity. Your project is saved on your machine and appears on Antigravity's home screen. Reopening brings it back exactly as you left it.

Quick start tomorrow: Open Antigravity → click your project → it opens in Local Mode → Terminal → git pull origin main → cd public; npx serve .. Ten seconds, no re-clone, no setup.

If Something Looks Different

Files missing, code changed, or things feel off

If you reopen the project and something looks different from how you left it — missing files, unexpected changes, an error at startup — inspect before you act. Don't delete, reset, or re-clone.

Terminal — investigate first
git status
# Which files changed and where are you?
git log --oneline -10
# Recent commit history — did someone merge new work?
git diff
# What exactly changed in your working files
  • See new commits from others? That's just new work that was merged. Pull it and continue.
  • See changes you didn't make? Compare against main and talk to the admin. Do not overwrite them.
  • Missing a file you know existed? Check git status first — it may have been renamed or moved. Never recreate from memory or from a fresh clone.

The golden rule: when unsure, inspect first and ask the admin. Never solve confusion by re-cloning, resetting, or deleting — that's how work gets lost.

Deploying to Production

Shipping merged work to the live site

Deploys run from a clean main after your PR is merged. Only deploy work that has been reviewed.

Terminal — deploy to Firebase Hosting
git checkout main
git pull origin main
npx -y firebase-tools@latest deploy --only hosting --project taxagentai062026

Production is instant. A bad deploy is visible to real tax clients immediately. Always test locally (Section 7) first. If something goes wrong, the admin can roll back from Firebase Console → Hosting → Release history.

Rules & Security

Non-negotiable, applies to every developer
  • No secrets in code. Never commit API keys, service-account JSON, or passwords. Firebase SDK config keys are public by design; private keys are not.
  • No client data in logs or chats. Don't paste real W-2s, 1099s, PII, or screenshots of client records anywhere outside the app.
  • Never push to main. Work in branches; merge via pull requests.
  • Never re-clone or reset the repo. Reopen your existing project; inspect before acting; never run destructive git commands.
  • Test locally before opening a PR. The portal must boot and core flows (login, 2FA, documents) must work.
  • Match the design system. Use the Emerald CSS variables (--accent, --bg-primary, etc.) — don't hardcode ad-hoc colors.
  • Keep .firebase/ and .env out of git. They are ignored for a reason.

Source of Truth

Where the real, current version of everything lives

Understand the layers so you always know which copy is authoritative:

GitHub (remote)The one true source of the codebase
Your local folder (your one clone)Your working copy, synced via pull/push
Antigravity project (Local Mode)Points at your local folder — reopens it, never re-creates it
Local server (npx serve)Serves public/ so you can test
Live site (Firebase Hosting)taxagentai062026.web.app — updated by deploy

When these disagree, GitHub main is the truth. Your local folder must be synced to it (git pull before work, git push via PR after). The live site is whatever was last deployed. If a copy feels wrong, don't trust it and don't delete it — sync from GitHub, then inspect, then ask if unsure.
