GitHub Branch Protection & Workflow

Overview: Protected Branches

Why the main branch must be locked down

For the Magnitax portal, the repository uses a protected main branch + feature branches + pull requests. This is the single most effective way to keep the live portal stable: nobody — including you — can push broken code straight to production by accident.

Goal: give developers permission to build, but make main something they can only change through your controlled review process.

2

Recommended Workflow

The branch flow every change must follow

Every change moves through the same funnel. Nothing touches main except a merged, reviewed pull request:

Developerstarts a feature branch
feature/magnitax-portalbuild · test · commit
Pull Requestreview + checks
protected mainmerge gate: approvals + checks
Productionlive portal (Firebase Hosting)

Rule of thumb: if a commit didn't go through a pull request, it doesn't belong in production.

3

Protect main

Turn on branch protection in GitHub

Step 3.1 — Open Branch Protection

  1. Open the Magnitax portal repository on GitHub.
  2. Go to Settings → Branches.
  3. Create a branch protection rule for main.

Step 3.2 — Turn On These Rules

  • ✓Require a pull request before merging — no direct pushes.
  • ✓Require approvals — ideally 1 or more reviewer approvals.
  • ✓Require status checks to pass before merging.
  • ✓Require branches to be up to date before merging.
  • ✓Block force pushes — history stays intact.
  • ✓Restrict who can push to matching branches if appropriate.

Do not allow the developer to bypass these rules unless absolutely necessary. The review gate is the whole point.

4

Developer's Normal Process

What the developer does every day

The developer should never build directly on main. Instead:

Terminal — start a feature branch
git checkout main
git pull origin main

git checkout -b feature/magnitax-portal

They make their changes and commit:

Terminal — commit & push the feature
git add .
git commit -m "Build Magnitax portal dashboard"
git push -u origin feature/magnitax-portal

Then they open a Pull Request → main. You review the changes before they can enter main.

Remember: the developer creates the branch, writes the code, and opens the PR. You approve and merge it after review.

5

Even Better: Separate Production from Development

Multiple safety layers as the portal grows

For a client-facing Magnitax portal, the target branch layout is:

BranchPurpose
mainProduction
developDevelopment / integration
feature/*Individual developer work

And ideally, changes flow through every layer before reaching customers:

feature/*
develop
staging
main
production

Why: this gives you multiple safety layers instead of relying on the developer not to make a mistake.

6

The Key Rule

The one thing to remember

Give the developer permission to build, but make main something they can only modify through your controlled review process.

Without this, a single developer can overwrite the live portal, leak client data, or take the site down — and you won't have a review checkpoint to catch it.

7

Setup Checklist

Verify every item before a developer starts
  • ✓Branch protection rule exists for main.
  • ✓PR required before merging into main.
  • ✓Approvals required — 1+ reviewer.
  • ✓Status checks required and up to date.
  • ✓Force pushes blocked on main.
  • ✓Push restricted to matching branches (admins/approved roles).
  • ✓Developer added with Write access only — not bypass privileges.
  • ✓Handed the developer the developer-facing workflow guide.
  • ✓Recorded the grant (date, developer, roles) in the operations log for the audit trail.
