Adding Developers to the Magnitax Portal Project

This training walks CPA Admin and Operations staff through the safe, repeatable process of adding a software developer to the Magnitax Secure Client Portal project — from repository and cloud access, to the daily workflow and production deploys.

Overview & Roles

What the project is and who is allowed to touch it

The Magnitax Portal is a single-page web application hosted on Firebase Hosting. It stores code on GitHub and uses Firebase Authentication, Firestore, and Storage for its live backend. Adding a developer means granting them access in two places:

SystemWhat the Developer GetsAccess Level
GitHub Clone, read, push to branches, and open pull requests on the repository Write
Firebase Console View the hosting project, read/write Firestore & Storage for their assigned work Editor
Firebase Hosting Deploy to preview/site URLs from their machine via the CLI Editor + Deploy

Principle: least privilege. Developers get only the roles needed for their task. Production owner and IAM management stay with the admin who completes this training.

2

Prerequisites

Confirm the developer has everything before granting access

Accounts

  • A GitHub account (their email must match what they will commit with).
  • A Google account that can join the Firebase project.
  • Node.js v18 or newer and npm installed (verify with node -v).
  • Git installed and configured (verify with git --version).

Verification Commands

Terminal — check the developer's environment
# Run as the developer, on their machine
node -v
npm -v
git --version
git config user.name
git config user.email

Note: commit identity must be set before the first push, or GitHub will reject the developer's commits.

3

Clone the Repository

Get the code onto the developer's machine

The repository lives at github.com/whoisdesirtech/Designing-Magnitax-Client-Portal. The developer clones it and serves it locally:

Terminal
git clone https://github.com/whoisdesirtech/Designing-Magnitax-Client-Portal.git
cd Designing-Magnitax-Client-Portal/public
npx serve .
# Opens the portal at http://localhost:3000 (or similar)

Important: the deployable app lives in the public/ folder. The developer must edit files inside public/ — the portal's entry point is index.html, with app.js (application logic) and style.css (design system).

4

Firebase CLI & Login

Connect the developer's machine to the Firebase project

The project targets Firebase hosting site taxagentai062026 (defined in .firebaserc). The developer installs the CLI, logs in, and selects the project:

Terminal
npx -y firebase-tools@latest login
# Opens a browser; the developer signs in with their Google account
npx -y firebase-tools@latest use taxagentai062026
# Now using project taxagentai062026

Never run firebase login --reauth or logout on a shared machine. Each developer keeps their own CLI session.

5

Granting Developer Access

The actual add-a-developer procedure

Step 5.1 — GitHub Repository Access

  1. Open github.com/whoisdesirtech/Designing-Magnitax-Client-Portal.
  2. Click Settings → Collaborators and teams.
  3. Click Add people (or Add teams for groups).
  4. Enter the developer's GitHub username/email.
  5. Choose role Write — allows pushing branches and opening pull requests, but not pushing straight to main.
  6. Send the invitation; the developer must accept it from their email or GitHub notifications.

Rule: developers push to feature branches and merge through Pull Requests. Direct pushes to main are reserved for admins.

Step 5.2 — Firebase Project Access

  1. Open console.firebase.google.com and select project taxagentai062026.
  2. Go to Project settings → Users and permissions (or the IAM page).
  3. Click Add member and enter the developer's Google account email.
  4. Assign the Editor role for their assigned work.
  5. Optional: grant Firebase Hosting Admin so they can deploy hosting sites.
IAM RoleCan DoRecommended For
Viewer Read project resources Contract review / read-only auditing
Editor Read & write Firestore, Storage, functions Active feature developers
Owner Everything, including billing & IAM Admins only — never granted in this training

Never grant Owner. Owner rights include billing and permission management and must stay with the Magnitax admin.

Standard Dev Workflow

Branch → commit → pull request → merge

Every change follows the same flow so production stays stable:

Terminal — feature branch workflow
git pull origin main
git checkout -b feature/jf-fix-login-error
# ... make edits in public/ ...
git add .
git commit -m "feat: describe the change"
git push origin feature/jf-fix-login-error

Then the developer opens a Pull Request on GitHub from the feature branch into main. An admin reviews the diff, verifies it locally, and merges.

Why it matters: every merge keeps a clean history, and the review step catches security mistakes before they reach real client data.

7

Deploying to Production

Publish merged changes to the live site

Deploys are run from a clean copy of main. Only admins or approved developers with Hosting Admin deploy.

Terminal — deploy to Firebase Hosting
git checkout main
git pull origin main
npx -y firebase-tools@latest deploy --only hosting --project taxagentai062026
SiteURL
Client & Admin Portalhttps://taxagentai062026.web.app
Landing Pagehttps://taxagentai062026.web.app/landing.html
Training (this page)https://taxagentai062026.web.app/training.html

Deploy only after a merged, reviewed PR. Firebase Hosting releases are near-instant, so a bad deploy is visible to clients immediately.

Rollback

If a deploy misbehaves, roll back to the previous release in the Firebase Console under Hosting → Release history — click the previous release and choose Rollback.

8

Security & Compliance

Non-negotiables for anyone touching the portal
  • No secrets in code. Never commit API keys, service-account JSON, or passwords. Firebase SDK config keys are public by design; private keys are not.
  • Environment files. Secrets belong in .env or Firebase environment variables — and .env files must stay in .gitignore.
  • Client data stays in Firestore/Storage. Do not log, copy, or paste real client documents or PII into chat, tickets, or screenshots.
  • Least privilege. Revoke access when a developer's contract or engagement ends (GitHub collaborator + Firebase IAM member).
  • Audit trail. Admin sessions, logins, document previews and downloads are already logged in the portal. Deploys are visible in Firebase release history.

Troubleshooting

Common issues when onboarding a developer
SymptomCauseFix
git push rejected (403) Invitation not accepted, or the developer used the wrong account Re-send the GitHub invitation; verify the account email
Command requires authentication on deploy Firebase CLI session missing or wrong account Run npx -y firebase-tools@latest login with the account added in Step 5.2
Wrong project in firebase use Developer selected another project Run npx -y firebase-tools@latest use taxagentai062026
Changes not showing after deploy Browser cache, or edits made outside public/ Hard-refresh; confirm files are under public/ and committed
No access to Firestore data Developer is Viewer (read-only) or not a project member Add the developer as Editor

Onboarding Checklist

Verify every item before a developer begins work
  • ✓Accounts. Developer has a GitHub account and a Google account.
  • ✓Environment. Node.js 18+, npm, and Git installed; git identity configured.
  • ✓GitHub. Collaborator added with Write access; invitation accepted.
  • ✓Firebase. Developer added as Editor in the Firebase project; logged in via CLI.
  • ✓Repo. Cloned and serving locally from public/.
  • ✓Rules. Reviewed branch/PR workflow, deploy policy, and security rules above.
  • ✓Access log. Recorded the grant (date, developer, roles) in the operations log for the audit trail.
